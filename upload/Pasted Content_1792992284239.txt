# MASTER BUILD PROMPT — ENTREPRENEURSHIP CLUB DIGITAL PLATFORM

## ROLE AND ENGINEERING RESPONSIBILITY

Act as a Senior Full-Stack Engineer, Software Architect, DevOps Engineer, Application Security Engineer, Database Engineer, and Technical Product Designer with extensive production engineering experience.

You are responsible for designing, implementing, testing, documenting, and preparing a complete Entrepreneurship Club platform for production deployment.

Do not build a collection of disconnected UI mockups. Build a coherent, modular, functional application with a working database schema, authentication, authorization, email automation, event management, messaging, video-conferencing integration, automated tests, and deployment documentation.

Follow these principles:

- Prefer simple, maintainable architecture over unnecessary complexity.
- Use the least expensive managed services that satisfy the requirements.
- Write type-safe, modular, reusable code.
- Enforce security in the backend and database, not merely in the user interface.
- Make all critical workflows observable and recoverable.
- Use database migrations instead of undocumented manual schema changes.
- Never claim a feature works unless its implementation and tests support that claim.
- Never fabricate successful integrations, email deliveries, security checks, or deployment results.
- Do not guarantee that the application is bug-free; systematically test and minimize defects.

Your objective is to build a real digital platform for the Entrepreneurship Club at ALTA School of Technology, Ajeenkya DY Patil University, Pune.

# 1. PRODUCT VISION

Build a modern, responsive, fast, professionally designed Entrepreneurship Club website and community platform.

The platform must provide three distinct experiences:

1. **Public website:** Visitors can discover the club, explore members and leadership, browse previous events, view public announcements, register for events, and apply for membership.
2. **Member workspace:** Approved and authenticated users can manage their profiles, view authorized announcements, send messages, participate in group conversations, and join video meetings.
3. **Private administration panel:** Authorized administrators and faculty users can manage applications, members, teachers, roles, permissions, events, announcements, email automation, moderation and operational settings.

The landing-page visual design will be refined separately later. Build a polished initial design with reusable components and a flexible design system so that the complete visual layer can later be changed without rewriting business logic.

The product must be designed to start on free tiers, with explicit resource limits and upgrade paths.

## Core priorities

1. Public website and content.
2. Secure authentication and membership registration.
3. Role-based admin panel.
4. Event registration and management.
5. Announcement and email automation.
6. DevOps, testing, backups and security.
7. Private messaging.
8. Multi-participant video conferencing and screen sharing.
9. Optional future machine-learning features.

Do not implement machine learning merely for decoration. It is not required for the first release.

# 10. DATABASE RLS AND API SECURITY

Every exposed table must have explicit authorization policies.

Examples:

- Users can update their own permitted profile fields.
- Public visitors can read approved public profiles.
- Public announcements are readable by everyone.
- Internal announcements require the proper audience and session.
- Only authorized reviewers can access private applications.
- Only participants in an authorized conversation can read its messages.
- Users cannot modify another user's registration.
- Admin actions require the correct permission and resource scope.
- Storage uploads must follow ownership and visibility rules.
- Secret credentials are never exposed in frontend code.

Build automated RLS tests for both successful and forbidden operations.

Simulate direct requests from visitors, pending applicants, normal members, club leads, faculty reviewers, admins and Super Admins.

Test privilege escalation attempts and ensure unauthorized database/API access is denied even when the frontend is bypassed.

Use database functions or Edge Functions for sensitive operations that require multi-step authorization or transactional behavior.

# 12. EVENT REGISTRATION PIPELINE

The public homepage is the entry point for public event registration.

Workflow:

1. Visitor opens an upcoming event.
2. Registration form appears on the homepage or a homepage-linked section.
3. The server verifies the event is published and registration is open.
4. The server checks the deadline and available capacity.
5. Duplicate registration is prevented.
6. The registration record is persisted.
7. An email confirmation is queued.
8. The admin dashboard updates registration counts.
9. A scheduled job sends configured reminders.
10. Attendance can be recorded by authorized staff.
11. Completed events are archived with approved content.

Do not allow registration for a cancelled, unpublished, closed or full event.

Support appropriate guest registration or authenticated member registration without exposing private profile information.

---

# 13. ANNOUNCEMENT PIPELINE

Workflow:

1. Authorized editor creates a draft.
2. Editor chooses the audience.
3. Content is previewed.
4. Editor publishes immediately or schedules publication.
5. The backend validates permission.
6. The announcement becomes visible to the authorized audience.
7. Unique email jobs are generated for eligible recipients.
8. The worker processes the email queue.
9. Provider results are recorded.
10. The admin panel displays delivery status.

Support draft, scheduled, published and archived states.

Prevent accidental duplicate campaigns.

Require confirmation before bulk sending.

Create a clear separation between website publication and email delivery so that temporary provider failures do not delete or lose the published announcement.

# 19. MONITORING AND BACKUP PIPELINES

Monitor:

- Frontend deployment health.
- Authentication failures.
- Database errors and capacity.
- Edge Function errors and latency.
- Email queue depth and failures.
- Realtime errors.
- Video-room failures.
- Security events.
- Backup freshness and restore status.

Use provider dashboards and structured application logs initially. Add extra observability infrastructure only when there is a concrete need.

## Backup pipeline

1. Schedule database export.
2. Validate export completion.
3. Encrypt backup.
4. Store it in restricted off-site storage.
5. Back up necessary Storage API objects separately.
6. Record timestamp and checksum.
7. Apply a documented retention policy.
8. Restore to an isolated test environment.
9. Verify schema, data and object integrity.
10. Record the test result.

Define an RPO and RTO based on club needs.

Never claim a backup is verified unless it has actually been restored successfully.

Do not retain application records, messages or personal information indefinitely without a documented reason.

Create automated tests verifying:

- Visitors cannot access private admin data.
- Members cannot grant themselves privileges.
- The last Super Admin cannot be accidentally removed.
- Duplicate applications are correctly handled.

- Members cannot modify another member's profile.

- Unauthorized users cannot receive video-room credentials.
- Upload rules prevent unauthorized access.
- Database migrations are reproducible.
- Critical browser journeys work after deployment.
- Backup restoration verifies schema, records and storage objects.

A feature is done only when:

- Implementation is complete.
- Relevant tests pass.
- Authorization rules are verified.
- Loading, error and empty states exist.
- Documentation is updated.
- Deployment and recovery are understood.
- No unresolved critical security problem is knowingly shipped.

# 23. WORKING RULES FOR THE CODING AGENT

Follow this execution protocol strictly.

1. Start by inspecting the existing repository, installed dependencies and current application state.
2. Identify any existing implementation that can safely be reused.
3. Create a file-based implementation plan and feature checklist.
4. Configure the foundation before implementing application features.
5. Implement in the phases above, keeping each phase testable.
6. After each meaningful change, run relevant type checks, tests and builds.
7. Fix discovered errors instead of continuing with a broken baseline.
8. Use actual Supabase schema migrations and RLS policies.
9. Use real API integrations when credentials and configuration are available.
10. If credentials are unavailable, implement a well-defined provider interface and an explicit development/test mode; clearly mark the integration as unconfigured rather than claiming it works.
11. Never insert fabricated member records, email-delivery results or meeting credentials into production.
12. Never bypass security checks to make a feature appear functional.
13. Keep the application usable when email or video providers are temporarily unavailable.
14. Do not request secrets through chat or write them into tracked files.
15. Do not ask unnecessary clarification questions. Use documented, conservative defaults, list assumptions and continue.
16. When a phase is incomplete, report the missing implementation and exact blocker.
17. Preserve existing working features when refactoring.
18. Keep architecture and deployment documentation synchronized with the code.

When using a tool-capable coding environment, inspect files and run commands directly rather than merely writing instructions for the user to execute.

Do not generate an enormous set of unconnected files without validating imports, dependencies, database contracts and application behavior.
